# Making dsh-developer the default development companion

Strategy proposal, 10 September 2026. The findings below describe the starting point at repository basis `4bf78c2` plus existing Mac support changes. Implementation has since begun; the [development guide](development.md) describes the current supported workflow, and the [platform guide](platforms.md) distinguishes exercised environments from remaining coverage. This proposal is not a claim that every milestone is complete. Upstream source basis: [`c291e7961a515f6d7af9304e7fd1d257929aef26`](https://github.com/deepseek-ai/deepseek-harness/tree/c291e7961a515f6d7af9304e7fd1d257929aef26).

**The product promise should be a completed development task.** A person brings an idea, a broken plugin, or a DSH change. The agent finds the relevant implementation, makes a focused change, runs it in the intended environment, repairs failures, and leaves code another developer can maintain. The human supplies domain intent and consequential choices; the agent supplies the DSH expertise. The critical measure is how much DSH-specific investigation and intervention the human still has to supply.

The initial audience is people developing for DSH: plugin authors, maintainers, and people changing the harness itself. Ordinary coding facilities—editing, navigation, commands, tests, Git, terminals, browser checks—belong in that workflow. Expanding into a general replacement for every coding environment would dilute this purpose. Win those developers' repeated use first.

**What the current repository establishes.** It has valuable native integration: one skill, a native tool registry entry, commands, and a CLI; substantive static audits; exact-version compatibility checks; and bounded execution and UI controllers. Keep and reuse these investments. The main gaps are connections from those capabilities to complete user outcomes.

| Finding | Evidence and limit | Product consequence |
| --- | --- | --- |
| Creator promotion generates a skill bundle, not arbitrary functionality. | A local render experiment requested a `search-docs` tool. The generated entry injected only `skills`, contained no `tools.register`, and retained the tool intention in Markdown. This is consistent with [templates.js](../lib/templates.js); it is not a test of what an agent could subsequently implement. | Build ordinary functioning plugins directly. Keep promotion as the narrower skill-export feature. |

Upstream published [0.1.5-rc.2](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.5-rc.2) on September 10. No compatibility with that release was tested here. | Make target discovery and knowledge refresh part of the product. Preserve old evidence without presenting it as current coverage. |
| The shipped references primarily cover audits, safety, and specialized execution. | [SKILL.md](../skills/dsh-developer/SKILL.md) has no general authoring or upstream-navigation reference family. [capabilities.js](../lib/capabilities.js) inventories selected runtime capabilities; it is not an architecture or symbol index. | Supply task-specific source navigation, examples, and implementation guidance. |
| Isolation covers small offline edits. | The documented cell export limits are 4 MiB, 256 files, and 512 KiB per file; dependency trees are excluded. [Platform guide](platforms.md). | It cannot be the universal route for dependency installation, Web builds, or a complete upstream checkout. |
| Ordinary plugins lack a supported runtime-verification path. | [compatibility-internal.js](../lib/compatibility-internal.js) admits only this product or reproducible promoted bundles; [doctor.js](../lib/doctor.js) skips ordinary plugins' tests and install lifecycle. | Add an explicitly authorized route for existing projects; a static pass cannot mean ready to ship. |
| Build fixes the target to the agent's workspace and validates `headless`. | [native-cell-workflow.js](../lib/native-cell-workflow.js) uses the root session directory and a fixed profile. | Resolve the actual package/subdirectory, plugin versus upstream project, and intended profile within authorized workspace scope. |
| Browser control is separate from server ownership. | [UI control](../lib/ui-cli-internal.js) reaches host loopback; [Apple cells](../lib/lab/apple-container.js) publish no ports and Build disposes them before returning. | Own server startup, readiness, browser reachability, repair/restart, and cleanup as one development session. |
| Common environments have incomplete coverage. | CI lists Windows and macOS. [exclusive-rename.js](../lib/exclusive-rename.js) rejects Linux promotion. Older/Intel Macs lack an admitted isolated provider. | Define and test support by workflow and environment, including native Linux. |
| Conversational quality remains unmeasured. | [skill-route.test.js](../test/skill-route.test.js) checks wording and size. The focused Creator/skill suite passed 14 tests, but none demonstrates an agent discovering a good solution from a vague request. | Add ordinary task trials and maintenance follow-ups, keeping these distinct from deterministic tests. |

A local capability run also witnessed this product installing, registering, and uninstalling in a disposable profile on macOS arm64 with Node 24.19.0 and DSH 0.1.1-rc.2. A static Doctor run passed with warnings and runtime checks skipped. Neither establishes that an arbitrary authored plugin works.

**Demand signals favor reliable completion.** Public reports describe [missing recovery from a broken Web plugin](https://github.com/deepseek-ai/deepseek-harness/discussions/2229), [a missing upstream export causing repeated boot failure](https://github.com/deepseek-ai/deepseek-harness/discussions/5864), and [dependency resolution before a profile's first launch](https://github.com/deepseek-ai/deepseek-harness/discussions/5537). A community [plugin manager](https://github.com/deepseek-ai/deepseek-harness/discussions/5858) addresses independent development and delivery. These are examples of actual problems and adjacent solutions, not a representative ranking of demand or proof that the reports remain unresolved in today's release.

**Organize around six user jobs.** Natural language stays the entry point. Deterministic operations should be callable through the same implementation from DSH, the CLI, and an external coding agent.

| User job | What dsh-developer should finish | Decisive demonstration |
| --- | --- | --- |
| Create from an idea | Infer a useful scope; choose an existing integration, configuration, skill, or new plugin; implement a usable first version. | The chosen solution achieves the inferred outcome through DSH, including relevant empty/error cases. Existing facilities may suffice without a new plugin. |
| Repair an existing plugin | Locate the failing package/service and cause; patch the existing repository; reproduce and fix the failure. | The original reproduction passes, and the unrelated working behavior remains intact. |
| Develop and inspect UI | Start an isolated development profile, expose its URL and logs, exercise the rendered UI, and stop cleanly. | Real Host/Client communication, two sessions, reload, and error recovery work. |
| Package and share | Build an ordinary bundle, test the actual archive in a clean profile, and produce install/recovery instructions. | A second environment installs and uses the packed artifact without the author's checkout. |
| Upgrade DSH or a plugin | Resolve exact targets; find affected consumers; implement migrations and revalidate behavior. | The feature works on the claimed versions; unsupported versions remain explicit. |
| Change DSH itself | Map the behavior to owning packages and consumers; reproduce the defect; implement and validate a focused upstream change. | An upstream-native regression and relevant checks pass at a recorded commit. |

Start with a dependency-bearing TypeScript native tool plugin, add a Web interface early, and also exercise one upstream bug fix. These cases expose different architectural requirements early. Do not make finishing an entire template catalog a prerequisite for useful development.

**Make DSH knowledge an executable resource.** Reuse upstream's [subsystem index](https://github.com/deepseek-ai/deepseek-harness/blob/c291e7961a515f6d7af9304e7fd1d257929aef26/docs/subsystems/README.md), source, tests, tutorials, and examples. Its subsystem declarations already have source-equivalence checks; a second hand-maintained API encyclopedia would create another drift problem.

Resolve the installed runtime or selected checkout before choosing guidance. Record its version/commit and package identities. Return a small, relevant source set: owning service, public declaration, a working consumer, lifecycle requirements, tests, and known differences from another target. For a tool this includes registration, schema/output handling, execution and cancellation; for UI it includes Client Modules, Remote methods, Slots, and scoped state. Do not silently substitute current master documentation for an older installation.

Begin with a curated task-to-source map and exact-source search. Add a generated symbol/service/dependency index only where representative navigation tasks show it saves meaningful work. Keep reusable examples compiled and exercised against their stated targets. Match knowledge refresh to upstream changes and invalidate affected examples and claims. A source checkout is a development target even when it is outside certified release lanes; unsupported safety-sensitive operations still require actual review.

For core work, read the checkout's instructions and select its existing gates. Current upstream separates Host and Client compilation and generated Remote types; its [development guide](https://github.com/deepseek-ai/deepseek-harness/blob/c291e7961a515f6d7af9304e7fd1d257929aef26/docs/development.md) explains the dependencies. A generic `npm test` recommendation does not cover that workflow. The tool should explain a change through actual callers and tests, not merely name a package.

**Make execution fit ordinary development.** Use DSH's existing workspace, filesystem, shell/subprocess, jobs, approval, and diagnostic services where the selected version supplies the required behavior. Use existing editor/navigation and external-agent facilities when that is where the person works. Keep DSH-specific decisions and operations shared; avoid rebuilding a parallel terminal, permission system, package manager, or agent scheduler.

Separate an authorized development workspace from execution of unknown downloaded code. The normal development route must support the repository's real dependency manager, lockfile, build artifacts, relevant network access, and long-running development server under the host's actual policy. An edit request alone must not manufacture execution authority. Untrusted execution retains its isolation requirements. Reuse the current cells for workloads they support; add a dependency-capable isolated route only with explicit installation, credential, network, process, transfer, and cleanup semantics. Do not obtain broader support by merely raising size limits or removing checks.

Create a disposable development profile and preserve the user's working profile. On failure, retain useful logs and offer one concrete recovery action. Cancellation must stop owned work and leave an intelligible state. Test the base workflow on native Windows, macOS, and Linux; test WSL independently. Cover paths with spaces/non-ASCII characters, package-manager wrappers, occupied ports, missing dependencies, and restart. Optional VM/browser setup should be requested when its capability is needed, with exact prerequisites and recovery.

Upstream already has a [dynamic Cordis prototyping route](https://github.com/deepseek-ai/deepseek-harness/blob/c291e7961a515f6d7af9304e7fd1d257929aef26/docs/user/develop/practice/dynamic-cordis.md). Evaluate and reuse it where appropriate. Its temporary plugins can affect other sessions in the process, so in-memory prototyping and distributable package development need distinct completion criteria.

**Teach development judgment through DSH examples.** For plugin-capability requests, a useful public guide should show concrete choices: use configuration when sufficient; reuse a service or MCP integration when it already does the job; add a thin native tool for a new capability; add a service/provider split when consumers actually need substitution. Investigate a core extension when those surfaces cannot express the requirement. For upstream changes, repair the owning subsystem and its consumers, following the checkout's conventions; a possible plugin workaround does not make a core bug fix inappropriate.

For “I want DSH to remember our project,” first inspect the workspace and available facilities. Distinguish durable project conventions from searchable documents or personal session recall. Propose the likely shared need and a small implementation, marking assumptions; ask only when the distinction changes the result. For “search our docs,” begin with retrieval and source attribution, then introduce indexing, UI, or multiple providers only if the workload needs them. Generalization should explain the user's concrete examples and a plausible variation without turning every idea into a platform.

Judge the code through real maintenance: add another source/provider; change configuration; unload and reload the plugin; diagnose a failure. Prefer typed native APIs, bounded modules, explicit disposal/cancellation, actionable errors, and tests of behavior. Avoid empty abstraction layers, duplicate registries, catch-all fallbacks that hide failures, placeholder functionality, and tests that only assert the generated structure. Follow the destination repository's conventions rather than imposing a new universal style system.

**Keep private authoring methods private.** Write the public behavior guidance independently from DSH's public conventions and observable developer needs. A small set of domain-specific examples and expectations can improve intent handling and maintenance without shipping a general-purpose private framework. Do not export private source, prompts, internal terminology, routing machinery, research records, or framework dependencies. Review the repository, history, examples, and npm archive together; excluding a file from npm does not remove it from a public Git repository. Similarity checks can assist review, but cannot prove that cumulative disclosures reveal nothing. Keep private research and provenance outside the public repository.

**Build in an order that tests the promise.**

1. **Baseline, demand, and target selection.** Observe a small initial cohort of plugin authors and upstream contributors doing their own tasks; use their recurring obstacles to revise the proposed priorities. Select the initial plugin and upstream tasks from that work, recording the current workaround and recurring cost. Run representative tasks with the same model, permissions, tools, and budget, with and without dsh-developer. Include an existing plugin and a core issue. Establish the supported release, current candidate, and source-checkout modes; record current failures before changing prompts or gates.
2. **One complete native-tool workflow.** Use an ordinary TypeScript plugin with a justified dependency. Implement source lookup, project creation/adoption, dependency installation under explicit execution policy, development-profile lifecycle, real invocation, repair, and artifact installation. Accept it only when a second person can use the output and make a small follow-up change. Also require successful relevant build/test execution in the first upstream checkout at this stage, to expose assumptions specific to small generated plugins; the complete upstream fix can follow in step 4.
3. **Dependencies, UI, and host coverage.** Carry a realistic dependency-bearing plugin through build, browser verification, packaging, and recovery. Add native Linux coverage and test Windows/macOS/WSL separately. Resolve ordinary execution before expanding specialized isolated providers.
4. **Upgrade and contributor workflows.** Feed upstream changes into source guidance and examples; exercise a real cross-version repair and a core regression. Preserve useful old lanes while adding newly demonstrated ones. Prepare a patch and reproduction when external submission is unavailable.
5. **Validate repeated use.** Return to those authors with their next tasks and include new users. Prioritize recurring blockers, publish reproducible examples and verified support results, and seek inclusion in upstream/community development resources after the workflows earn the recommendation.

Upstream's inspected [contribution policy](https://github.com/deepseek-ai/deepseek-harness/blob/c291e7961a515f6d7af9304e7fd1d257929aef26/CONTRIBUTING.md) currently does not accept external PRs and directs reports to Discussions; it recommends the `dsh-plugin` topic for discovery. Core development remains useful for internal contributors and local patches. Recheck policy before offering submission. Outreach and publication are proposed work, not actions performed in this inquiry.

**Measure outcomes rather than feature count.** Keep a small set of ordinary requests covering the six jobs, a misleading initial request, an interrupted task, and a maintenance change. Include Chinese and English requests. Compare equivalent baseline and assisted conditions, preserve failures, and use fresh variants after examples have shaped the implementation.

Success means helping developers complete useful work with less DSH-specific investigation, fewer avoidable mistakes and maintainable results at reasonable cost. It does not require error-free software of arbitrary scale. Compare the same model on representative tasks with and without the plugin, under comparable tools and budgets. A discovered defect warrants a repair to the affected artifact; it does not by itself establish that the plugin made development worse or that the model cannot perform the task. Prioritize failures caused by wrong DSH knowledge, broken integration, omitted relevant checks, repeated known mistakes or claims beyond the evidence. Scale verification to the change and its consequences, meet the project's required gates, and state remaining uncertainty. Endless review is not a completion criterion.

Record task completion, time to first working behavior, human interventions, unnecessary questions, setup failures, runtime regressions, and effort for a second maintainer to change the result. Model-generated code needs actual execution evidence where claimed; intent quality and maintainability need independent human judgment. Repeat variable agent tasks before claiming reliability. Unit tests, compilation, source checks, and runtime conformance answer different questions and should keep separate results.

A release should describe exactly which workflows work on which hosts and DSH versions. Set quantitative improvement targets after measuring the baseline. The eventual adoption claim requires people choosing the product again for another task; neither passing CI nor adding more operations establishes that.

The next implementation should therefore complete the dependency-bearing native-tool workflow and its comparison task, together with version-aware source guidance. Broadening the execution lab or compressing another prompt is lower priority unless that concrete workflow demonstrates the need.
